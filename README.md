# Визуальный веб-редактор конфигураций LLM-агентов

Веб-редактор иерархических YAML-конфигураций агентов и скиллов IDE-плагина «Veai»: разбор Markdown-файлов с frontmatter в графовую доменную модель, интерактивное редактирование графа, валидация (ссылочная целостность, циклы, симметрия связей), round-trip-экспорт обратно в файлы с сохранением комментариев и неизвестных полей YAML.

## Личная роль

Внешнего форка или upstream-репозитория нет, прикладная логика написана с нуля. Стек выбран осознанно (гл. 1.2.2 записки): React 19 + TypeScript + Vite на клиенте, Node.js + Express 5 на сервере, Vitest 4 для тестов, `@xyflow/react` для рендера графа, `yaml` v2 для round-trip-парсинга.

Первые два коммита приносят в репозиторий внешний Markdown-материал, переданный командой плагина «Veai» как образец реального формата конфигураций — он лежит в `rules/`, `tasks/`, `scenarios/` и частично в `agents/`/`skills/`. Это тестовые данные, не авторский код, в зачёт объёма не идут.

## Что нетривиального в реализации

Ключевые места (подробно — гл. 2.2 и 3.1 записки):

- **Каноническая модель связи с `RelationOrigin[]`** — `server/domain.ts:556-589`. Одна связь, заведённая со стороны агента (`agent.skills`) и со стороны скилла (`skill.use-by`), сворачивается в одно ребро с двумя `origin[]`. Это основа инварианта симметрии и кода `RELATION_ONE_SIDED`.
- **Отложенный матчинг ссылок** — `server/domain.ts:33-39`, `:636-655`. Пользователь может временно сослаться на ещё не существующий узел; такие ссылки складываются в `PendingReference[]` и пересопоставляются после каждой мутации.
- **Поиск циклов с маршрутом** — `server/domain.ts:837-891` (`detectAgentCycles`). DFS со стеком пути, выдающий человекочитаемый маршрут `A -> B -> C -> A`.
- **Round-trip YAML** — `server/domain.ts:907-944` + `parseDocument(..., { keepSourceTokens: true })`. При экспорте переписываются только канонические поля; комментарии, порядок, посторонние ключи и тело Markdown остаются нетронутыми.
- **Защита от path traversal** — `server/repository.ts:36-46` (`resolveInsideRoot`), покрыта негативным тестом.
- **Типизированные точки подключения React Flow** — `src/components/ConfigNode.tsx:13-14`. Скилл — только `target`, агент — `source` и `target`; запрещённая связь «скилл → агент» физически не создаётся в UI.

## Архитектура

Серверная — трёхуровневая (гл. 2.1.3, рис. 2.5):

1. `server/index.ts` — тонкий HTTP-слой (Express), делегирует в `SessionManager`.
2. `server/domain.ts` — `SessionManager` как единственный владелец состояния + парсер документа, нормализация связей, синхронизация YAML-проекций, валидатор, экспортёр.
3. `server/repository.ts` — файловый I/O с защитой от выхода за корень.

Клиент (гл. 2.1.3, рис. 2.4): `<ReactFlow>` + `ConfigNode`, формы и панель Advanced в `src/App.tsx`, API-слой в `src/api.ts`. `App.tsx` намеренно остаётся одним файлом — в записке он прямо назван «центральным элементом клиентского контейнера» (гл. 3.1.1).

Общий контракт типов — `shared/types.ts` (используется и клиентом, и сервером).

## Запуск и сборка

Требования: Node.js ≥ 20, npm ≥ 10.

```bash
npm run dev              # сервер на :3001 + Vite-клиент на :5173
```

В dev-режиме клиент проксируется к серверу через `vite.config.ts`. Демо-рабочее пространство (`agents/` и `skills/` в корне репо) загружается через `GET /api/demo/documents` и сразу открывается в редакторе.

Чтобы открыть свою рабочую область, доступны три способа:

1. Положить свои `agents/` и `skills/` в корень репо и нажать «Reload workspace».
2. `WORKSPACE_ROOT=/путь/к/проекту npm run dev` — задать корень через переменную окружения.
3. В UI развернуть «Advanced» и использовать поле «Workspace path» + «Open from path». Этот режим использует `POST /api/sessions/open-from-path`.
